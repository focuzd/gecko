## 3. Data and tokenizer

### 3.1 Dataset

TinyStories V2 (GPT-4 generated), from Hugging Face (`roneneldan/TinyStories`).

| Dataset key | File | Characters used | Vocabulary | Used by |
|---|---|---|---|---|
| `tinystories` | `TinyStoriesV2-GPT4-valid.txt` (~20 MB) | first 5,000,000 | 84 characters | bigram, MLP, `gpt-10.8m-c256-d5m-b64`, encoder-decoder tests |
| `tinystories-train` | `TinyStoriesV2-GPT4-train.txt` (~2 GB) | first 50,000,000 (about 60 MB downloaded) | 96 characters | every `d50m` model |

Only as much of the file as needed is downloaded. A few characters in the source file are broken quote marks that show up as `�`; we kept them, so they are part of the vocabulary and also appear in some reference stories.

**Split:** the text is encoded, then the first 90% is training data and the last 10% is validation data. For 50M characters that is 45M for training and about 5M for validation.

**Batches:** `get_batch` picks random starting points in the training data and cuts out windows of `block_size` characters. The target for each position is the next character.

### 3.2 Tokenizer

`CharTokenizer` sorts every distinct character in the text and numbers them. `encode` turns a string into numbers and silently drops unknown characters; `decode` turns numbers back into a string. The vocabulary is stored in each checkpoint, so a model always decodes with its own vocabulary.

The end-of-story marker `<|endoftext|>` is 13 ordinary characters, not a special token. The sampler stops when the last 13 generated characters spell it.

## 4. Models in detail

All models share the same interface: `forward(idx, targets)` returns logits for every position (and the loss if targets are given), and `generate(idx, n)` samples `n` new characters.

### 4.1 Bigram (`bigram.py`)

One embedding table of size vocabulary × vocabulary. Row *i* holds the logits for the character after character *i*.

- Parameters: 84 × 84 = **7,056**
- It only ever looks at the current character. It was trained with windows of 8 characters, but the window length doesn't change what it can see, which is why its name says `c1`.

### 4.2 MLP (`mlp.py`)

Following Bengio et al. (2003) and Karpathy's makemore part 2:

1. Embed each of the last 32 characters as a 24-number vector.
2. Concatenate them: 32 × 24 = 768 numbers.
3. Linear layer to 512 hidden units, then tanh.
4. Linear layer to 84 logits.

To train on every position at once, like the other models, the input is left-padded and cut into 32-character windows with `unfold`.

| Part | Parameters |
|---|---|
| Embedding 84 × 24 | 2,016 |
| Hidden layer 768 × 512 + 512 | 393,728 |
| Output layer 512 × 84 + 84 | 43,092 |
| **Total** | **438,836** |

### 4.3 GPT (`gpt.py`)

A decoder-only transformer from Karpathy's "Let's build GPT":

- Token embedding plus learned position embedding.
- 6 blocks, each: LayerNorm → multi-head causal self-attention → residual add → LayerNorm → feed-forward (Linear 4× wide, ReLU, Linear) → residual add.
- Final LayerNorm and a linear layer to the vocabulary.
- Dropout 0.2 after attention projection and feed-forward. Weights initialised from a normal distribution with standard deviation 0.02.
- Attention uses PyTorch's fused `scaled_dot_product_attention` with a causal mask. We checked it against the original step-by-step attention on a trained model: outputs differ by at most 0.000007, which is rounding noise. The heads still run one after another in a loop, and an unused `tril` mask buffer is kept so older checkpoints still load.

**Parameter count for the 10.9M model** (vocab 96, width 384, context 512):

| Part | Calculation | Parameters |
|---|---|---|
| Token embedding | 96 × 384 | 36,864 |
| Position embedding | 512 × 384 | 196,608 |
| Attention (per block) | 3 × 384 × 384 (Q, K, V) + 384 × 384 + 384 (projection) | 590,208 |
| Feed-forward (per block) | 384 × 1536 + 1536 + 1536 × 384 + 384 | 1,181,568 |
| LayerNorms (per block) | 2 × 768 | 1,536 |
| 6 blocks | 6 × 1,773,312 | 10,639,872 |
| Final LayerNorm + output layer | 768 + 384 × 96 + 96 | 37,728 |
| **Total** | | **10,911,072** |

With a 256 context the position table is half as big, giving 10,812,768 (10.8M). The 19.3M model uses width 512 and 8 heads (each head still 64 wide), giving **19,266,656** parameters at context 512.

| Config | Layers | Width | Heads | Head size | Context | Parameters |
|---|---|---|---|---|---|---|
| `gpt` | 6 | 384 | 6 | 64 | 256 | 10.80M (vocab 84) / 10.81M (vocab 96) |
| `gpt` at `--block-size 512` | 6 | 384 | 6 | 64 | 512 | 10.91M |
| `gpt-20m` at `--block-size 512` | 6 | 512 | 8 | 64 | 512 | 19.27M |

## 5. Training

### 5.1 Settings

| Config | Batch | Context | Steps | Eval every | Learning rate | Eval batches |
|---|---|---|---|---|---|---|
| `bigram` | 32 | 8 | 3,000 | 300 | 0.01 | 200 |
| `mlp` | 64 | 32 | 10,000 | 1,000 | 0.001 | 200 |
| `gpt`, `gpt-20m` | 64 | 256 | 5,000 | 500 | 0.0003 | 200 |
| `encdec` (all splits) | 64 | 512 | 5,000 | 500 | 0.0003 | 200 |
| `encdec-tiny` | 32 | 128 | 2,000 | 250 | 0.001 | 50 |

- Optimiser: AdamW with PyTorch defaults apart from the learning rate. No learning-rate schedule or warmup.
- Random seed: 1337.
- Precision: fp32 for every trained model. fp16 mixed precision exists behind `--amp` but has not been used yet, so it can be tested as its own experiment. Runs using it get `-fp16` added to their name.
- **Context and batch interaction:** if `--block-size` is given without `--batch-size`, the batch shrinks to keep characters per step the same (64 × 256 = 32 × 512 = 16,384). This rule is behind the key finding in [section 8.2](#82-context-256--512-at-batch-32).
- Checkpoints in `weights/checkpoints/` are saved at every evaluation together with the optimiser state, so `--resume` can continue an interrupted run. The final model goes to `weights/<run name>.pt` with its config, vocabulary, settings and loss history.

### 5.2 Where training ran

The bigram, MLP and first GPT were trained locally on CPU. All `d50m` GPTs were trained on a free Kaggle **NVIDIA T4** GPU through `kaggle/train.ipynb`, which clones this repository, trains, evaluates, samples, writes the 24 benchmark stories, and saves everything to Kaggle's Output tab. The 10,000-step run most likely hit Kaggle's 12-hour session limit right after training, so its benchmark stories were generated locally with the same seeds.

### 5.3 Run names

`<model>-<parameters>-c<context>-d<data>-b<batch>[-fp16]`, built automatically from the actual settings by `utils.run_name`. Names do **not** include the number of steps; the training-setup table in `result.md` does.

Older names used before 25 October: `gpt-5m` = `gpt-10.8m-c256-d5m-b64`; `gpt-50m` = `gpt-10.8m-c256-d50m-b64`.

## 6. The benchmark in detail

### 6.1 Generation

- **6 prompts in 3 groups** (familiar, altered, unfamiliar), shown in [report.md section 4.2](report.md#42-the-story-benchmark). Every prompt was checked to use only characters in the vocabulary.
- **4 stories per prompt**, so 24 per model. Story *k* of prompt *p* uses seed `1000 × p + k`, identical for every model.
- **Temperature 0.8**, no top-k, at most **600 new characters**, stopping early at `<|endoftext|>`.

### 6.2 Controls

- **12 real TinyStories stories**, picked with a fixed random generator (seed 0) from the held-out 10% of the 5M-character text, longer than 200 characters. Each one's first 4 words act as its "prompt", and it is cut to the prompt plus 600 characters, the same length limit as model stories. These set the 100 mark.
- **6 random-character strings**: 600 characters drawn uniformly from the vocabulary (without newlines), each after one of the benchmark prompts. These set the 0 mark.

### 6.3 Judging

The rubric (in `src/judge.py`) scores 7 criteria from 1 to 5, each with written anchors:

| Criterion | 1 | 3 | 5 |
|---|---|---|---|
| spelling | mostly non-words | many misspelled or made-up words | no spelling mistakes |
| grammar | no sentence structure | sentences exist but are often broken | fluent and grammatical |
| consistency | no stable characters or facts | names, roles or facts change partway | characters and facts stay consistent |
| prompt_following | ignores the opening | loosely related | a natural continuation |
| structure | no story | some events, no clear arc | clear setup, events and resolution |
| meaning | nonsense | sentences make sense, the whole doesn't | clear cause and effect |
| style | nothing like a children's story | partly | simple words and short sentences, suitable for a 3-4 year old |

The judge is told the stories may be cut off at a length limit and not to penalise that. It writes a justification first, then the scores, as JSON.

**Who judged:** we started with Google's `gemini-3.8-flash` on the free tier, through `judge.py`. It scored 15 stories, then hit the free tier's request limits (HTTP 429 errors). Those 15 partial scores were discarded. All reported scores are from **Claude Haiku 5.5**, run as one fresh sub-agent per story, given only the rubric and that one anonymised story. The first round judged 90 stories (72 from three models, plus 12 real and 6 random). Every later model added 24 more. During the first round, a few stories were judged a second time by another Haiku agent with the same task file; this moved the MLP's score from 19 to 18.

**Scores:**
- **weighted** = (spelling + grammar + prompt_following + style + 1.5 × (consistency + structure + meaning)) / 8.5
- **normalised** = 100 × (weighted − random mean) / (reference mean − random mean), where the random mean is 1.12 and the reference mean is 4.25.

Example: the best model's weighted score is 2.77, so its normalised score is 100 × (2.77 − 1.12) / (4.25 − 1.12) = 52.7, shown as 53.

### 6.4 Automatic metrics

All four look only at the generated part of a story (the prompt is removed), with words taken as lowercase runs of letters and apostrophes.

- **Real-word rate:** share of generated words that occur at least 3 times in that model's own training text.
- **Distinct-2:** unique word pairs ÷ all word pairs.
- **Ended on its own:** share of stories that produced `<|endoftext|>` within 600 characters.
- **Longest copied span:** the story is scanned with 8-word windows, and each window is checked for an exact match in the training text. The longest chain of consecutive matching windows gives the span (a chain of *r* windows is *r* + 7 words long). Anything shorter than 8 words counts as 0. Since 18 October each model is checked against its own training data, so 50M models are checked against their 45M training characters; the reference and random rows are checked against the 5M text.

### 6.5 Statistics

For two models, stories with the same prompt and seed are paired, and the difference in weighted score is computed for each pair. We report wins, ties, the mean difference, and a **paired sign-flip test** p-value (randomly flipping the sign of each pair's difference many times). For the first context investigation we also ran an unpaired permutation test and a paired bootstrap confidence interval.

## 8. Experiment by experiment

Letters refer to the models in [report.md section 5.2](report.md#52-changing-one-thing-at-a-time): A = `gpt-10.8m-c256-d50m-b64`, B = `gpt-10.9m-c512-d50m-b32`, C = `gpt-19.3m-c512-d50m-b32`, D = `gpt-10.9m-c512-d50m-b64`, E = `gpt-19.3m-c512-d50m-b64`.

### 8.1 Data size: 5M → 50M characters

- **Held fixed:** architecture (10.8M, 6 layers, 6 heads, width 384, context 256), 5,000 steps, batch 64, so both saw 82M characters.
- **Changed:** the training text (5M from the validation file vs 50M from the training file).
- **Result:** 45 vs 46. Per criterion almost identical: spelling 4.04 vs 4.04, consistency 2.08 vs 1.96, meaning 1.83 vs 1.88, weighted 2.54 vs 2.55. Copied span 8.0 vs 7.8 words.
- **Reading:** the 5M model already saw its data about 18 times without overfitting badly, so data wasn't the bottleneck at this size and budget.
- **Caveat:** different files, so not a pure size comparison, and validation losses aren't comparable.

### 8.2 Context: 256 → 512, at batch 32

- **Held fixed:** model (6 × 384), 50M data, 5,000 steps, characters per step (64 × 256 = 32 × 512 = 16,384), fp32.
- **Changed:** context 256 → 512, which halved the sequences per step (64 → 32), from 320,000 to 160,000 sequences in total.
- **Result:** loss 0.661 → 0.638 (lower), score 46 → 40 (worse). Spelling 4.04 → 3.50, consistency 1.96 → 1.71, distinct-2 0.91 → 0.83, ended on its own 71% → 58%. Prompt following went up (2.75 → 3.00). Familiar prompts equal (49 vs 49); the drop was all in altered (39 → 33) and unfamiliar (49 → 37).
- **Loss was still falling** at the end: 0.669 at step 4,000, 0.654 at 4,500, 0.642 at 5,000.

**Investigation.** We checked for hidden causes:

| Possible cause | Check | Result |
|---|---|---|
| Different vocabulary or data | compared checkpoints | identical 96 characters in the same order, same 50M text: ruled out |
| New attention code | old vs new attention on the c256 weights | max logit difference 6.7 × 10⁻⁶: ruled out |
| Generation bug | regenerated 3 stories per model | all 6 match the benchmark stories exactly: ruled out |
| Resume or logging glitch | read the loss history | 11 clean evaluations: ruled out |
| Story boundaries in windows | counted `<|endoftext|>` per window | in 60% of 512-character windows vs 30% of 256 ones; present, but the gap stays in story-aligned tests |
| **Where the loss improved** | loss by position | **the cause** (below) |

Loss by position, with each test window starting at the beginning of a story, the way generation works:

| Characters of story so far | A (c256) | B (c512, b32) |
|---|---|---|
| 0-32 | **0.282** | 0.305 |
| 32-128 | **0.538** | 0.563 |
| 128-256 | **0.589** | 0.608 |
| 256-383 | 0.629 | **0.622** |

On random held-out windows, B's loss was 0.688 on positions 0-255 and 0.591 on positions 256-511. On the same targets with only 256 characters of context, A scored 0.650 and B 0.670. So **all** of B's lower average loss comes from positions beyond 256 characters, and most of a 600-character benchmark story is written before that point, where B is worse.

**Why:** short-range prediction is learned at the start of every training sequence. With half as many sequences, B got about half the practice at it.

**Effect on the stories:** B kept reusing rare words from the opening and garbling them. Prompt words reappeared in the story body 21 times for B vs 3 for A on the scientist prompt, and 20 vs 5 on the robot prompt. B produced made-up forms such as "scien", "scient", "sciss" and "scissient" (10 such words vs 1 for A), and "Zed and Zed was scared… When Zed showed Zed Ged". That explains both the lower spelling score and the slightly higher prompt-following score.

### 8.3 Size: 10.9M → 19.3M, at context 512 and batch 32

- **Held fixed:** 6 layers, context 512, batch 32, 5,000 steps, 50M data, fp32.
- **Changed:** width 384 → 512 and heads 6 → 8 (head size stays 64).
- **Result:** loss 0.638 → 0.613, score 40 → 44. Better on every criterion: spelling 3.50 → 3.79, consistency 1.71 → 1.92, structure 1.96 → 2.12, meaning 1.79 → 1.92. Best altered-prompt score so far at that point (43). Lowest spread of any GPT (weighted std 0.26).
- **Against A:** no real difference (−0.04 weighted, p = 0.57) despite much lower loss.
- **Copying:** longest copied span 9.79 words, above real stories (8.75).
- **Loss still falling:** 0.644 → 0.624 → 0.617 over the last three evaluations.

### 8.4 Batch: 32 → 64, at context 512

- **Held fixed:** model (10.9M), context 512, 5,000 steps, 50M data, fp32.
- **Changed:** batch 32 → 64. This also doubled the characters per step (32,768) and the total characters seen (164M) and the compute.
- **Result:** loss 0.638 → 0.588, score 40 → **51**, p = 0.002. Highest of the GPTs at that point on every criterion except prompt following (tie): spelling 4.04, grammar 2.88, consistency 2.17, meaning 2.00 (all 24 stories got exactly 2), style 3.50. Ended on its own 75%, distinct-2 0.87, copied span 7.92.
- **Reading:** B's drop came from too few sequences, not from the longer context. With enough sequences, the longer context beats A on every prompt group (56 / 45 / 51 vs 49 / 39 / 49).
- **Caveat:** D also saw twice the characters of A, so "longer context" and "more training" are mixed in D vs A. The clean check is a c256 model trained on 164M characters (batch 128, or 10,000 steps), not done yet.

### 8.5 The "how far can we get" run

- **Setup:** 19.3M parameters, context 512, batch 64, **10,000 steps**: 328M characters seen, about 4× the compute of D. Not a one-factor run.
- **Result:** loss **0.516** (train 0.506), score **53**. Best spelling (4.25), grammar (2.96) and structure (2.38). Meaning 2.04 and consistency 2.08 barely moved.
- **Against D:** +0.06 weighted, 12 of 24 wins, p = 0.39: no real difference.
- **Copying:** longest copied span 10.58 words, the highest of all models.
- **Endings:** ended on its own only 46% of the time (D: 75%).
- **Reading:** diminishing returns. The extra compute went to surface fluency. More passes over the same 50M characters start to trade generalisation for memorisation, so further training should use more data.

### 8.6 Attention heads (not tested separately)

The 10.9M models use 6 heads and the 19.3M models 8, always with head size 64. Heads were never changed on their own, so the size comparison in 8.3 measures "wider with more heads", not heads alone.

## 9. The encoder-decoder

### 9.1 Design (a small learning version)

Instead of separate input and output texts, each 512-character training window is split in two, like T5's prefix language-model objective:

```
[ ..... older 256 characters ..... | ..... newest 256 characters ..... ]
  encoder: reads all at once,         decoder: predicts the next character,
  no causal mask                      causal, and cross-attends to the encoder
```

- **Encoder block:** same as a GPT block but without the causal mask.
- **Decoder block:** causal self-attention → **cross-attention** to the encoder output → feed-forward.
- **Shared token embedding** for both sides, with one extra PAD token.
- **Loss only on decoder positions.**
- **While generating:** the decoder works alone for the first 256 characters (encoder all PAD), and the encoder fills with older text after that.
- **Padding instead of masks:** empty encoder slots hold the PAD token, which the model learns to ignore.
- **Training mix:** in 2/3 of training windows the encoder side is cut short (about half of those to empty, half partly filled), so training matches what happens during generation.

**A fix along the way:** the first version filled the encoder first and gave the decoder only the last character. Story openings came out garbled ("Once upon a timer Thed besoo the t…"), because that case gets almost no training. Giving the decoder the most recent text fixed it, with the same loss.

### 9.2 Configurations (vocabulary 96, context 512)

| Config | Layers | Width | Heads | Head size | Encoder | Decoder (incl. cross-attn) | Of which cross-attn | Shared embedding | Total | vs GPT D (10,911,072) |
|---|---|---|---|---|---|---|---|---|---|---|
| `encdec` | 3 enc + 3 dec | 360 | 6 | 60 | 4,769,280 | 6,362,376 | 1,558,440 | 34,920 | 11,166,576 | +2.3% |
| `encdec-2e4d` | 2 + 4 | 348 | 6 | 58 | 3,003,240 | 7,892,040 | 1,941,840 | 33,756 | 10,929,036 | +0.2% |
| `encdec-4e2d` | 4 + 2 | 366 | 6 | 61 | 6,538,956 | 4,425,768 | 1,073,844 | 35,502 | 11,000,226 | +0.8% |

All three use batch 64, 5,000 steps, learning rate 0.0003, dropout 0.2 and the 50M data, matched to model D. Run names: `encdec-11.2m-c512-d50m-b64`, `encdec-2e4d-10.9m-c512-d50m-b64`, `encdec-4e2d-11.0m-c512-d50m-b64`. **None has been trained at full size yet.**

### 9.3 Tiny test run (`encdec-tiny`, CPU)

- 962,004 parameters: width 128, 4 heads, 2 + 2 layers, context 128 (64 + 64), batch 32, 2,000 steps, learning rate 0.001, dropout 0.1, 5M data.
- Validation loss by step: 4.464 (0) → 1.991 (250) → 1.560 (500) → 1.381 (750) → 1.311 (1,000) → 1.278 (1,250) → 1.248 (1,500) → 1.208 (1,750) → **1.173** (final, train 1.160).

**Loss by encoder fill** (`evaluate.py`, at least 200 fixed batches):

| Encoder side | Validation loss |
|---|---|
| empty (0 characters) | 1.1881 |
| full (64 characters) | 1.1826 |
| gap (empty − full) | **+0.0055** |

**Loss by decoder position**, empty vs full encoder:

| Decoder position | Empty encoder | Full encoder |
|---|---|---|
| 0 | 2.377 | 2.356 |
| 1 | 1.824 | 1.795 |
| 4 | 1.244 | 1.229 |
| 63 | 1.157 | 1.157 |

At position 0, the decoder has 1 character of its own plus 64 in the encoder, yet the loss barely moves. **The tiny model hardly uses its encoder.** Likely reasons: only the first few decoder positions really need the encoder, so its training signal is weak, and two thirds of training windows have a shortened encoder side.

**Tiny layer-split checks** (width 96, 64 + 64, 500 steps): 2e4d validation loss 4.47 → 1.59, 4e2d 4.43 → 1.62. Both wrote "Once upon a time…" openings. Encoder gap 0.0001 for both.

### 9.4 Comparing with the GPT

The encoder-decoder's overall loss only covers decoder positions, which always have 257-512 characters of context, so it **must not** be compared with a GPT's overall loss. Instead, `evaluate.py` prints, on the same fixed windows:

- for a GPT, the loss on positions 0-255 and 256-511;
- for an encoder-decoder, the loss with an empty and with a full encoder.

"GPT first half" lines up with "encoder empty", and "GPT second half" with "encoder full". For model D these are **0.6341** (positions 0-255) and **0.5520** (positions 256-511), a gap of 0.082. Those are the targets for the full encoder-decoder runs.

Between the three encoder-decoder variants, validation loss **is** comparable (same split, data and vocabulary), as long as it comes from `evaluate.py` and not the training log.

**Recommended run order:** `encdec` (3+3) first as the reference, then `encdec-2e4d`, then `encdec-4e2d`.

## 11. Known limitations

- One training seed per setting, so run-to-run variation is unknown.
- 24 stories per model and 8 per prompt group.
- One judge model; no human scores and no second judge. Judge drift over time has not been re-checked.
- Model D vs A and model E vs anything change more than one factor.
- The 5M and 50M data come from different TinyStories files.
- Reference stories come from the 5M text, and a few contain broken `�` characters, which may lower the 100 mark slightly.
- Run names don't record the number of steps.
- In the Kaggle notebook, choosing `MODEL = "gpt"` with `BLOCK_SIZE = 512` trains at batch 32, not 64, unless `--batch-size 64` is added.

## 12. How to reproduce

Run from the repository root. On the development machine, PyTorch is installed in the Windows Python, so use `py`.

Train (CPU or GPU):
```bash
py src/train.py --model gpt --dataset tinystories-train --block-size 512 --batch-size 64
```

Evaluate:
```bash
py src/evaluate.py weights/gpt-10.9m-c512-d50m-b64.pt
```

Write stories:
```bash
py src/sample_stories.py --weights weights/gpt-10.9m-c512-d50m-b64.pt --num-stories 3 --seed 42
```

Benchmark a new model (generate its 24 stories, then build the report after judging):
```bash
py src/benchmark.py generate --weights weights/<run name>.pt --out outputs/<run name>_benchmark.jsonl
```
```bash
py src/benchmark.py import outputs/<run name>_benchmark.jsonl
```
```bash
py src/benchmark.py report
```

Print the encoder-decoder parameter table:
```bash
py src/encdec.py
```

On Kaggle: import `kaggle/train.ipynb`, choose a T4 GPU, turn Internet on, set `MODEL` and the other settings in the first cell, then Save & Run All.
